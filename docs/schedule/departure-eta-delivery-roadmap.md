기존 fail-closed 조건을 유지한다. 선택 경로의 공급자·노선·승하차 ID 매칭은 유지했다.

21:53 실행에서는 두 지하철 시간표가 연결돼 `TIMETABLE_PROVIDER`/`TIMETABLE_ONLY`와
65분 미래 여정이 생성됐다. 첫 열차가 현재 실시간 목록에서 확인되지 않아 정상 ETA는
채택하지 않았다. 공개 API는 이를 `futureTimetablePrediction`으로만 제공하고 정상 ETA
시각 필드는 닫았다. 원래 진단 UI 테스트가 모든 미채택 결과에 `저장 경로 기준`만 요구해
이 실행의 UI 검사는 실패했다. 이후 시간표 전용 경고와 각 열차 시각을 검사하도록 테스트를
보완했지만, 새 실제 미관측 표본에서 해당 미래 시간표 UI 분기를 재통과한 것은 아니다.
실제 Worker/공개 API 미래 시간표 감사와 합성 회귀 통과를 UI 통과로 대신하지 않는다.

최신 21:55:50 및 21:56:51 격리 평가에서는 동일 노원→사당→신림 경로의 두 시간표가
모두 연결됐고 시간표 모델의 이동시간은 67분이었다. 마지막 관측 원천은 21:52:40으로
약 251초 전이어서 120초 신선도 기준을 넘었다. 따라서
`TRANSIT_ARRIVAL_SOURCE_STALE`, `stale=true`, `accepted=false`,
`predictedArrivalAt=null`을 유지했다. 앱은 실제 UI에서 두 번 모두
`차량 관측정보 오래됨 · 저장 경로 기준` 및 기존 안전 출발 22:09를 표시했다.
원래 ODsay 추정 60분, 앞선 다른 시각의 시간표 65분, 최신 시간표 67분은 서로 다른
근거/조회시각의 값이며 지도 오차나 실제 이동 오차로 해석하지 않는다.

새 ODsay 선택 경로 준비부터 실제 Worker→공개 API→지정 시뮬레이터를 검증했다.
시간표 연결과 실패 시 안전 표시는 확인했지만 정상 실시간 ETA UI 채택은 0회,
진단 UI 통과는 2회로 전체 실제 공급자 E2E는 **PARTIAL**이다.
이번 단계에서 호출 한도 오류는 없었으며 원천 갱신이 오래됐다는 이유로 신선도 기준을
완화하거나 시간표를 실시간으로 표시하지 않았다. 실제 새 피드로 정상 첫 열차와 환승을
채택하는 ODsay 앱 E2E, 지도 2분 정확도와 실제 이동 정확도는 남아 있다.

## 다음 계산 변경 전 확인: 출입구↔승강장 시간의 소속 구간

2026-10-11 공식 규격과 공개 환승 자료를 다시 확인했지만, 현재 자료만으로 역 내부 이동의
소속 구간을 확정할 수 없다. [Tmap 규격](https://transit.tmapmobility.com/docs/routes)은
`sectionTime`을 구간별 소요시간, `totalWalkTime`을 총 보행자 소요시간으로 정의한다.
확인한 규격에는 출입구↔승강장 시간이 WALK/SUBWAY 중 어디에 포함되는지 명시돼 있지 않다.
검색에서 근거를 찾지 못했다는 뜻이며, 공급자가 해당 정보를 전혀 보유하지 않는다는 뜻은 아니다.

현재 `TransitJourneyTimetableEnricher.enrichWith`는 WALK 원본 초를 유지하고, SUBWAY 구간을
시간표 승하차와 대기/여유로 재구성한다. 따라서 역 내부 시간이 원본 SUBWAY 추정에만
포함되는 계약이라면 재구성 시 누락될 가능성이 있고, 이미 WALK에 포함되는 계약이라면
추가 가산은 중복이 된다. 어느 쪽도 현재 확인된 결함으로 확정하지 않는다.
도보 steps의 출입구 이름·노면 좌표만으로 실내 시간 포함 여부를 추론하지 않는다.

[서울교통공사 공개 환승정보](https://data.seoul.go.kr/dataList/OA-22521/L/1/datasetView.do)는
최단 환승 승하차 문 위치와 참고 소요시간이다. 출발역 접근/목적역 진출 시간을 제공한다는
근거로 사용할 수 없고, 다른 승하차 위치의 일반 보행시간으로 바로 대체하지 않는다.
앞서 보존한 사당 참고 7-3→6-1, 136초도 네이버의 5-2와 조건이 다르다.

### Tmap 문의 초안 — 미전송

> 대중교통 routes API의 지하철 도보 시간 범위를 확인하고 싶습니다.
> 1. 출발역 출입구→승강장, 도착역 승강장→출입구 시간은 WALK sectionTime에 포함되나요?
>    포함되지 않으면 SUBWAY sectionTime에 포함되나요, 아니면 전체 응답에서 제외되나요?
> 2. 지하철 간 환승 WALK sectionTime은 하차 승강장→승차 승강장 이동시간인가요?
>    대기시간이나 안전 여유도 포함되나요? 빠른 환승 승하차 문 위치를 확인할 필드가 있나요?
> 3. WALK start/end 명목 좌표와 steps의 끝점이 다를 때 시간·거리 산정 경계는 무엇인가요?

변환했다. 노원→사당→신림 조건에 맞는 변환 여정 3개의 도보는 총 9개였으며 새
메타데이터 검증을 통과했다. 그 뒤 진단 도구의 전역 `mappedWalks.size == 3` 가정이
실패했다. 이번에 재현한 실패는 HTTP/mapper 실패가 아니라 복수 후보를 하나로 센
진단 오류다. 이를 여정별 검사로 수정했으며, 같은 오류가 과거 모든 재조회 실패를
설명한다고 확대 해석하지 않는다. 후보별 도보 보존 회귀 테스트를 추가해 mapper
테스트 24개가 통과했다. 수정 후 별도 단독 API 재호출은 하지 않았다.

### 2 실제 Worker→API→설치 앱

테스트 일정 입력 snapshot을 새 메모리 H2에 복사하고 오늘의 미래 목표 시각을 생성했다.

실제 벽시계를 사용했고 push acknowledgement만 테스트 대역이다.

첫 실행은 실제 보정과 화면 검증 후, 펼친 시트에서 사라진 요약 버튼을 로그용으로
다시 읽는 테스트 오류로 실패했다. 두 번째는 한 회차 통과 후 이전 회차의 펼친 시트
상태가 남아 요약 버튼을 찾지 못했다. 검증한 label을 펼치기 전에 보관하고, 다음
회차는 접힌 시트로 시작하도록 XCUITest를 수정했다. 두 실행을 통과로 집계하지 않는다.

## 단계 3 전체 여정 보정

공급자 경로의 초 단위 도보와 운행 시간을 보존하고 실제 운행 시간표를 연결한다. 가까운 첫
승차만 검증된 실시간 차량으로 보정하고, 지연을 이후 환승까지 전파해 탈 수 있는 다음 차량을
시간표에서 다시 찾는다. 먼 미래 환승을 실시간 차량처럼 표시하지 않는다.

E2E는 정상, 첫 차량 지연 후 환승 회복, 다음 차량 부재, 시간표 근거 부족, 복구 후 마감 초과를
각각 확인한다. 원래 계획, 새 도착 예측, 시간 근거, 실패 사유를 혼동하지 않는다.

41분으로 갱신됐지만 아래 구간 안내는 저장된 4호선 49분·2호선 9분을 그대로 표시했다.
`buildEffectiveTransitRoutePresentation`은 `routeChanged=true`인 대체 경로에만 최신 여정 안내를
생성하고, 동일 경로에서는 저장된 경로 막대가 남는다. 최신 구간 시간과 원래 지도 geometry를
분리해서 표현하도록 변경했다. 현재 보정 여정은 평가된 구간 시간과 대기를 사용하고, 헤더와
지도는 저장 경로로 명시한다. 알림 기준 출발시각과 평가 여정의 출발시각은 덮어쓰지 않는다.
단순히 총시간에 맞춰 구간 시간을 비율 조정하지 않는다. 모의 공급자를 사용한 지정 시뮬레이터의
6개 앱 E2E가 통과했다. 정상·지연 후 회복에서는 보정 여정의 모든 구간을 표시하고, 시간표 부족·
환승 실패·마감 초과에서는 각각의 진단을 표시한다. 앱 표시 검증 중에는 격리 서버의 평가 시계를
고정했다. 실제 공급자 정확도나 기기 알림 전달을 검증한 결과는 아니다.

채택 가능한 ETA와 알람에 실제 적용한 시각을 연결한다. 실패한 조회값을 정상 결과처럼
채택하지 않고, 근거 없는 알람 지연을 막는다. 확정 환승 실패와 시간 근거 부족은 구분하며,
자동 취소했던 알람만 정상 회복 시 새 세대로 재예약한다. 사용자가 취소한 알람은 복구하지 않는다.

E2E는 동일 알람의 갱신·취소·복구와 이전 세대 차단, 평가 이력 보존, 앱 API 표시 일치를
확인한다. DB의 UPSERT 또는 CANCEL은 실제 OS 알람 반영·벨소리 실행과 별개다.

첫 보호 조건을 구현했다. `TrafficResult.accepted`인 정상 ETA 또는 확정 환승 실패만 자동 알람
변경을 요청한다. 시간표 부족·stale·조회 오류는 이력과 진단에 남기되 기존 알람을 변경하지 않는다.
관련 단위 테스트 97개, Worker 통합 테스트 2개와 지정 시뮬레이터의 6개 앱 E2E가 통과했다.
추가 경계에서는 미래 알람이 있는 상태에서 첫 저신뢰도 평가의 과거 출발시각을 반환시켰고,
알람 시각·세대·명령 상태가 모두 그대로 유지됐다. Worker 오류로 보존된 것인지도 배제했다.
취소 사유를 알람 상태에 추가 저장했다. `PAST_CONFIGURED_ESTIMATE`와
`TRANSIT_TRANSFER_FAILURE`만 정상 ETA에서 새 세대로 복구한다. 사용자·종료 취소인
`EXPLICIT_OR_TERMINAL` 및 사유가 없는 기존 CANCEL은 자동으로 복구하지 않는다.
환승 실패 후 UNKNOWN 평가를 거쳐도 저장된 취소 사유가 유지되므로 직전 ETA의 실패 코드에
의존하지 않고 복구한다. 사용자가 자동 취소 상태에서 다시 취소하면 사유 변경도 새 세대로
발행해 이전 자동 복구를 차단한다. 취소 사유는 서버의 판단 근거이며 기기 명령 형식은 유지한다.
관련 BE 테스트 135개, Python 검증기 회귀 44개와 9개 실제 시뮬레이터 앱 테스트가 통과했다.

단계 1에서 추가 재현된 경계도 포함한다. 사용자가 미래 일정을 저장했지만 기존 추정 소요시간으로
계산한 출발시각은 이미 지난 경우 설정 동기화가 CANCEL을 발행했다. 이번 경계 테스트에서
과거 추정시각 사유로 취소한 뒤 정상 ETA가 미래 출발시각을 제시하면 새 UPSERT로 복구됐다.
기존 사유 없는 CANCEL은 자동 취소로 추정하거나 일괄 갱신하지 않는다.

운영 반영에는 `migrations/2026-10-05-departure-alarm-cancellation-reason.sql` 적용이 필요하다.
별도 네트워크 격리 MySQL 8.0에서 선행 테이블·버전 부재 차단, 잘못된 컬럼 차단, 재적용,
기존 NULL 보존 및 CHECK 제약을 검증했다. 운영 DB에는 아직 적용하지 않았으며, 새 코드로
운영 서버를 재시작하기 전에 API·Worker를 중지하고 마이그레이션과 버전 마커를 확인해야 한다.

## 단계 5 실제 공급자 연결

Tmap은 현재 테스트 공급자로 사용하고 ODsay 포트는 유지한다. 공급자 전환 시 저장 경로의
노선·정류장 내부 ID를 다른 공급자로 해석하지 않는다. 운영 공급자 설정은 별도 배포 검증에
포함하며 기존 서버가 최신 코드나 활성 설정을 사용한다고 추정하지 않는다.

최신 실제 공급자 연결은 10월 12일 Tmap 및 ODsay 모두 정상 보정의 Worker/API/앱 연속
2회가 통과했다. ODsay의 관측 만료 후 읽기 진단도 통과했다. 공급자 연결 성공과 단계 7의
지도 대비 정확도는 별도이며, 아래 10월 7일의 미채택 내용은 당시 실패 기록이다.
10월 7일 낮 조회에서는 서울 API가 차량 2대를 반환했다. 이 응답은 한도 초과가 아니었지만
원천 갱신시각이 약 3분 전이고 선택한 시간표 열차와 일치하는 차량도 아니어서 보정으로
채택하지 못했다. HTTP 성공이나 차량 수신만으로 실제 공급자 앱 E2E를 통과시키지 않는다.
같은 날 12:33 재검증에서는 약 53초 전의 최신 차량 응답이 있었다. 그러나 4599번 차량의
노원 도착 예정 12:34:45는 좌표 출발 12:34 이후 역 접근 완료 12:39:42보다 빨랐다.
선택한 시간표의 4091번 사당행은 12:41:30 승차였고 실시간 응답에 없었다. 최신 응답을
받아도 탑승할 미래 차량의 근거가 없으면 보정하지 못하므로, 모든 미채택을 stale나
인증·한도 오류로 해석하지 않는다. 이 검사는 읽기 전용 공급자 연결 검사이며 앱 E2E가 아니다.
최신 동일 차량 근거를 확보해 승인된 테스트 경로로 검증하며, 한도 초과 반복 호출이나 여러
키를 통한 우회는 하지 않는다. 한도 오류와 미지원, 차량 없음, stale 결과를 구분한다.

## 단계 6 기기 알림 전달

시뮬레이터의 실제 로컬 OS 알림·벨소리 검증과 아이폰의 실제 푸시·벨소리 검증을 분리한다.
기기와 OS 기능 지원 범위는 대상 버전·권한·서명 설정에서 직접 확인한다. 새 권한이 필요하면
사용자가 직접 승인하며 테스트가 시스템 권한을 자동으로 수락하지 않는다.

각 조건에서 평가시각, 예약시각, 실제 수신·실행시각을 기록한다. 기존 예약보다 앞당기기,
뒤로 변경하기, 취소하기, 중복 알림 차단을 검증한다. OS 알람의 동작 방식이나 정시 실행을
데이터 없이 보장하지 않는다.

## 단계 7 실제 시간 정확도

동일 출발·도착 지점, 운행일, 요청 출발시각, 이동 방식·방향·종별을 고정한다. 역 플랫폼 경로와
거리 좌표 경로의 총시간은 직접 비교하지 않는다. 네이버의 표시 총시간과 요청시각부터 도착까지의
시간도 다를 수 있으므로 원본 타임라인을 보존한다. 카카오는 같은 미래 시각 설정을 확인할 때만
비교 표본에 포함한다.

표본마다 부호 있는 오차, 절대 오차, 근거, 제외 사유를 남긴다. 실제 이동 표본이 확보되면
절대 오차 중앙값, 95백분위, 120초 이내 비율을 계산한다. 표본 수와 실패율을 함께 공개하며
성공 한 건이나 지도 예측의 일치만으로 2분 이내 정확도가 확보됐다고 선언하지 않는다.

## 테스트 격리와 증거

전용 시뮬레이터의 고유 ID를 지정한 XCUITest로만 앱을 조작한다. 모의 공급자 E2E는 별도
loopback 서버와 메모리 H2를 사용하고 외부 호출을 하지 않는다. 기존 로컬 서버와 다른
시뮬레이터는 중단하거나 초기화하지 않는다. API 키·계정 비밀번호·토큰은 증거에 저장하지 않는다.

각 단계 결과에는 공급자 입력이 실제인지 모의인지, DB 범위, 앱 테스트 결과 묶음, 공개 API
응답, Worker 처리 횟수, 알람 상태를 기록한다. Unit·통합 테스트는 별도 결과로 표시하고
시뮬레이터 E2E 대신 제시하지 않는다. 테스트 전용 서버와 연결 설정은 종료 후 원복한다.

1초·1초·1초·0초이며 모두 알람 화면 진입과 끄기까지 통과했다. 잠금은 지정 창의 실제
