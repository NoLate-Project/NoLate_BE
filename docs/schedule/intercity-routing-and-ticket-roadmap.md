# NoLate 시외 길찾기와 승차권 연결 로드맵

기준일: 2026년 10월 15일
상태: 사용자가 요구한 일정별 운행편 조회·조건 전달 예매 연결은 미완료. 기존 iOS 단일 승차권 여정 MVP 구현. 기차·고속·시외버스 유형 보존, 운행편 선택, 공식 앱 우선 연결, 이미지·텍스트·단일 PDF 가져오기, 확인한 편 고정 연결, 중복 방지와 고정 출발 상태 반영. 현재 검증 결과는 아래 2026-10-13 절에 기록하며, 실기기·Android·전국 커버리지·원본 보관·취소 자동 동기화·P5 전체 완료와 구분한다.
우선순위: 시외버스 도보 오표시 복구 → 시외 경로 저장과 ETA 정합성 → 실제 운행편 연결 → 예매와 승차권 가져오기

플랫폼 진행 순서: **iOS 우선**(2026-10-12 사용자 지시). Android 구현·화면 E2E는 후속 작업으로 보류하며, 현재 iOS 단계의 완료 조건에서 분리한다.

최초 확인한 문제는 **시외버스 구간이 도보로 표시되는 오류**다. 아래 원인과 제약 표는 수정 전 소스 검토 기록이다. 현재는 기차·고속·시외버스 구간을 FE·BE에서 보존하고, 알 수 없는 구간을 도보로 바꾸던 처리를 제거했다. 공공 시간표의 단일 운행편을 여정에 적용할 수 있으며, iOS 공유 이미지·텍스트에서 사용자가 확인한 기차 정보를 저장하고 해당 시각을 고정해 앞뒤 경로를 연결할 수 있다. iOS 기차는 코레일, 버스는 티머니GO 앱 우선 연결을 제공하며 열 수 없으면 공식 웹을 연다. 버스타고는 공식 웹으로 선택할 수 있다. 기차·고속·시외버스 한 편의 이미지·텍스트·단일 PDF 가져오기를 지원한다.

최종 목표는 Apple Wallet 없이 `출발지 → 역 또는 터미널 → 예매한 기차 또는 버스 → 도착 역 또는 터미널 → 최종 목적지`를 하나의 개인 이동 계획으로 관리하는 것이다. 예매는 공식 서비스에서 하고, NoLate는 가져온 승차권에 맞춰 접근 경로·도착 후 경로·출발 알림을 연결한다.

## 2026-10-15 출시 범위 결정

사용자와 일정별 운행편 자동 조회·조건 전달 예매 연동을 출시 후 업데이트로 진행하기로 정했다. 1차 출시는 일정 관리·길찾기·출발 알림의 출시 검증에 집중한다. 정식 예매 서비스 참여·제휴 규격과 테스트 환경을 확보한 뒤 날짜·구간 자동 전달, 해당 날짜 편 조회, 예매 및 일정 반영을 후속으로 완성한다.

기존 공식 앱 메인 화면 연결을 출시 버전에 유지한다면 “공식 예매 앱 열기”로 기능 범위를 표현하고, 날짜·구간은 예매처에서 직접 선택해야 함을 안내한다. 이것을 일정 조건이 적용된 예매 연동으로 소개하지 않는다. 이 절은 출시 범위 결정 기록이며 제품의 기능 비노출·버튼 문구 변경을 완료했다는 뜻은 아니다. 실제 구매 표 공유·조건 전달 예매 E2E·알림 전달 등 미검증 사항과 전체 출시 준비도는 각각 별도로 확인한다.

## 2026-10-15 사용자 요구 정정: 일정에 맞는 운행편 조회와 예매 연결

사용자가 요구한 것은 시외 일정을 등록할 때 일정의 날짜·출발지·도착지와 도착 희망 시각에 맞는 운행편을 조회하고, 선택한 조건으로 공식 예매를 이어가는 기능이다. 예매 앱의 메인 화면을 여는 URL smoke 성공을 이 요구의 완료로 간주하지 않는다.

현재 소스의 시간표 화면은 경로 출발일을 운행일의 초기값으로 사용하고 날짜를 API에 전달한다. 그러나 시외버스 조회 서비스는 당일 외 날짜를 `DATE_UNSUPPORTED`로 거절하며, 공식 예매 버튼은 `dark`·`kind`만 받아 날짜·역/터미널·선택 편을 예매처에 전달하지 않는다. 따라서 미래 일정에 맞춘 시외버스 조회·예매 연결은 현재 구현으로 완성되지 않는다. TAGO의 [시외버스 공식 명세](https://www.data.go.kr/data/15098541/openapi.do)도 현재 당일 배차만 제공한다고 명시한다.

완료 기준은 다음과 같이 정정한다.

1. 일정의 한국 시간 날짜·도착 희망 시각과 실제 승하차 역/터미널을 조회 조건으로 연결한다. 자정 통과로 전날 탑승이 필요하면 탑승일을 명확히 표시하고 확인한다.
2. 출발지에서 승차 지점까지 이동·탑승 준비, 하차 후 목적지 이동을 포함해 일정에 도착할 수 있는 편을 제안한다. 미래 날짜를 오늘의 배차로 대체하지 않는다.
3. 해당 날짜의 운행편 조회 근거와 예매처의 실제 판매·잔여석 확인을 구분한다. 제공되지 않는 날짜나 노선을 매진·운행 없음으로 표시하지 않는다.
4. 공식 연동이 지원하는 범위에서 선택한 탑승일·출발·도착·편 조건이 적용된 조회/예매 화면으로 연결한다. 공식 앱의 조건 전달 계약은 아직 확인되지 않았으며 임의 파라미터를 만들어 구현하지 않는다. 메인 화면만 열리는 동작을 조건 전달 완료로 집계하지 않는다.
5. 실제 NoLate 일정 등록 화면에서 미래 날짜 변경 → 운행편 재조회 → 편 선택 → 예매처에서 같은 조건 적용 확인을 E2E로 검증한다. 구매는 사용자가 수행하며, 이후 실제 표 가져오기·일정 연결은 별도 검증한다.

이번 정정에서는 소스와 공식 제공 범위를 검토하고 요구·완료 기준을 갱신했다. 제품 UI나 네이티브 구현은 변경하지 않았다. 날짜별 조회 공급원과 공식 예매 조건 전달 계약을 확보하기 전에는 이 기능 전체를 완료로 표시하지 않는다.

## 2026-10-15 네이버 지도 사례와 공식 참여 경로 확인

[디지털서비스개방 KTX 적용사례](https://openservice.go.kr/ktxBook)는 네이버 지도에서 목적지 경로 검색 후 코레일 승차권을 예매하는 흐름을 실제 연계 사례로 설명한다. 따라서 기차의 정식 예매 기능은 지도 SDK만 추가하는 작업과 다르며, NoLate가 예매 서비스 연계 참여를 신청할 수 있는 공식 절차를 먼저 검토한다. 네이버 지도와 동일한 상용 계약이나 내부 구현이 NoLate에 그대로 제공된다고 가정하지 않는다.

- [KTX 개방서비스](https://www.openservice.go.kr/travelKtxBook), [SRT 개방서비스](https://openservice.go.kr/travelSrtBook): 서비스별 참여 가능 여부·현재 신청 대상·코레일 전용 웹 또는 API 연계 형태·날짜/역/편 조건 전달 범위를 지원센터에 확인한다.
- [수시신청](https://openservice.go.kr/onDemandApp): 기업·단체·법인 등을 대상으로 문서24 공문, 수요기관 신청서·이용계획서·사업자 증빙 등을 안내한다. 분기별 심의와 보안·CI 연계 요건이 명시돼 있다. NoLate의 자격·서비스별 추가 조건과 현재 수시 대상 포함 여부는 확인이 필요하며, 신청 즉시 인증키가 나오는 절차로 표현하지 않는다.
- [공식 연계 절차](https://openservice.go.kr/serviceProc): 수요기관 선정·협의, 이용 체결, 검증서비스 승인, 개발·연동 테스트, 운영 API 인증키와 운영 전환을 거친다.
- 시외·고속버스의 날짜별 운행편·판매 정보와 예매 조건 전달은 티머니/버스타고의 별도 공식 연동을 확인해야 한다. 기차의 디지털서비스개방 참여 경로를 버스에도 적용할 수 있다고 가정하지 않는다.
- [네이버 지도 공개 URL Scheme](https://guide.ncloud-docs.com/docs/maps-url-scheme)은 지도 검색·길찾기 등의 앱 호출을 문서화한다. 이번 공개 문서 확인에서는 특정 날짜의 기차 예매 화면을 자동으로 채우는 외부 호출 계약을 확인하지 못했다. NoLate에서 네이버 지도 길찾기를 여는 동작을 날짜별 예매 자동 연결 완료로 집계하지 않는다.

사용자가 선호한 공식 앱 이동형은 해당 예매처의 공식 조건 전달 링크가 제공되면 그 규격으로 구현한다. NoLate 안에서 네이버처럼 날짜별 표 목록·좌석·결제까지 제공하려면 정식 예매 서비스 연계의 제공 범위와 참여 승인을 확보한다. 외부 신청·문의는 이 조사에서 전송하지 않았고, 제품 코드·UI는 변경하지 않았다.

## 2026-10-15 실제 iPhone의 공식 앱 URL 실행 확인

사용자가 실기기 진행을 허용한 뒤 “지금은 표 없이 앱 전환만 확인”으로 범위를 지정했다. 최신 소스의 서명된 1.3.0(55)를 기존 앱 위에 업데이트 설치했고, iPhone 13 / iOS 26.6에서 현재 제품의 `korailtalk://gotoMainViewContoller`와 `tmoneytia://main/home`를 foreground 테스트 실행기의 `UIApplication.open`으로 전달했다. 수신 앱을 지정하지 않은 URL 라우팅에서 실제 코레일+ 5.0.16과 티머니GO 2.7.1의 foreground 실행·NoLate 복귀 2개가 모두 통과했다. 관련 FE 4 suites / 52 tests, 빌드·실기기 프로비저닝·서명·컴파일된 조회 허용 목록도 확인했다.

이는 실제 앱의 URL 라우팅과 복귀 smoke 검증이다. NoLate 예매 버튼의 화면 직접 조작부터 이어지는 전체 E2E, 예매처 메인 화면 로딩 완료, 실제 표 공유·저장·경로 연결, 알림·Live Activity 전달까지 확인한 결과가 아니다. 계정 로그아웃이나 일정 생성·수정·삭제를 하지 않았다. 설치 빌드는 운영 API와 TMAP을 사용하며 `.env` 및 운영 서버 배포는 변경하지 않았다. 화면과 원본 로그는 저장소 밖에 비공개로 보관하고 테스트 실행기만 제거했다. 아래 2026-10-13 절의 시뮬레이터 한정·실기기 보류는 당시 기록이다.

## 2026-10-13 iOS 단일 승차권 여정 MVP

이번 완료 단위는 `공식 예매처 열기 → 표 공유 → 기기 내 인식과 사용자 수정·확인 → 개인 일정 저장 → 승하차 장소 확인 → 고정 편의 앞뒤 경로 연결 → 저장·재실행 복원`이다. 원본·QR을 탑승용으로 보관하는 기능과 이동 중 안내 전체는 포함하지 않는다. 아래 2026-10-12 수치는 과거 단계별 기록이며 이번 최종 수치와 합산하지 않는다.

- 기차는 코레일 앱, 고속·시외버스는 티머니GO 앱을 우선 연다. 미설치·조회 오류·실행 실패는 수단별 공식 웹으로 연결하고, 시외버스에는 버스타고 공식 웹 선택도 제공한다. 공식 앱의 메인 화면만 열며 여정·개인정보를 URL에 넣지 않는다. 티머니GO 주소는 [공식 모바일 안내](https://txbus.t-money.co.kr/useinf/mobileInf.do)의 다운로드 연결에서 관찰한 주소이며, 실제 앱 버전의 수신 보장은 실기기 후속 검증 대상이다.
- 이미지·텍스트 및 잠기지 않은 1페이지 PDF를 받는다. PDF는 20MB 이하, 추출 텍스트는 32KB 이하로 제한하며 스캔 PDF는 기기 내 OCR을 사용한다. 여러 파일·여러 페이지 PDF는 거절한다. OCR은 날짜·터미널·등급을 사용자가 수정하고 명시적으로 확인해야 저장된다. 취소·환불 완료로 인식한 표의 저장은 차단한다.
- 기차는 열차번호, 고속·시외버스는 등급을 필수로 검사한다. 원본·OCR 원문·QR·좌석·결제정보는 서버로 보내거나 보관하지 않는다. 다른 공유 형식·무작위 티켓 ID로 같은 운행편을 다시 공유해도 서버가 개인별 중복을 막는다. 여러 승객·여러 좌석을 한 운행편의 개인 여정으로 취급한다. 기존 일정을 삭제하면 같은 편을 다시 가져올 수 있다.
- 표 변경·취소를 자동 조회하지 않는다. 상세 화면에 기존 일정 삭제와 유효한 새 표 공유 절차를 표시한다. 좌석 구매·잔여석·탑승홈·역 내부 동선은 예매처에서 확인한다.
- 최종 도착 희망 시각을 늦춰도 가져온 편과 접근 출발 시각을 늦추지 않도록 서버 출발 상태, 알림 작업 계획, Live Activity 투영을 수정했다. 새 실시간 근거가 없는 상태는 `stale / LOW`로 표시하며, 고정 시간표를 실시간 ETA로 승격하지 않는다. 알림 전송·Live Activity의 실제 기기 표시는 이번 시뮬레이터 검증 범위 밖이다.

API 일정만 삭제하고 화면 증거 일정은 별도 합성 계정에 남겼다.
- **최종 회귀:** FE 6 suites / 80 tests, typecheck, 신규 API 테스트 ESLint 및 API E2E 1개 통과. 이전 단계·반복 실행 수치와 합산하지 않는다. BE 코드 변경·BE 회귀 재실행·일반 ETA guard 배포 검증은 이번 범위가 아니다.
- **초기 실행 기록:** 최근 장소 이름 필드 오류, 복수 장거리 구간 선택, 테스트 쿼리 컴파일 오류, 화면 축약명 비교 오류를 수정했다. 전용 시뮬레이터가 앱 실행·캡처에 응답하지 않은 실행은 중단 후 해당 기기만 재시작했다. 초기 실패·빌드 실패·시뮬레이터 중단은 최종 통과와 구분해 검증 JSON에 기록했다.

이 결과로 대표 시외버스 한 편의 시간표 선택·연결·복원 검증을 완료했다. 전국 커버리지, 예매·잔여석·탑승홈·터미널 내부 경로·알림 전달은 확정하지 않는다. 다음 대상은 버스 공식 예매처의 앱 우선 연결과 승차권 가져오기다. 실기기와 Android는 계속 보류한다.

## 수정 전 오류의 원인

사용자가 확인한 증상은 “시외버스 경로가 도보로 나온다”이다. 현재 소스에는 다음 변환 경로가 있다.

```text
ODsay 시외버스 구간 trafficType 6
  → normalizeLegKind에서 ETC
      ├ 기본 RouteInfo에서는 TRANSFER로 생성
      └ 지도 세그먼트에서는 ETC 유지
          → routeStepTypeFromSegmentMode에서 WALK로 변환
          → 기본 RouteInfo와 병합하며 단계 type 덮어쓰기
          → 타임라인에 도보 아이콘 표시
```

기본 RouteInfo와 지도 세그먼트는 병렬로 만들어졌다가 화면 단계에서 합쳐진다. 따라서 단순히 `ETC → TRANSFER → WALK`라는 순차 변환만 고치는 것으로는 충분하지 않다. 원본 구간 종류를 공통 모델부터 유지해야 한다. 제목은 기존 단계의 문자열을 재사용할 수 있어 모든 화면에 반드시 “도보”라는 글자가 나오는 것은 아니지만, 도보 단계·아이콘으로 바뀌는 흐름은 소스에서 확인된다.

| 위치 | 확인된 동작 | 영향 |
| --- | --- | --- |
| `NoLate_FE/src/modules/map/odsayApi.ts:292` | trafficType 1·2·3만 지하철·버스·도보로 변환 | 열차·고속·시외버스는 ETC |
| `NoLate_FE/src/modules/map/tmapApiCore.ts:79` | TransitLegKind에 장거리 교통 종류 없음 | 후속 변환에 수단 정보를 전달할 수 없음 |
| `NoLate_FE/src/modules/schedule/routeInfo.ts:423` | BUS·SUBWAY 외 구간을 TRANSFER로 생성 | 일정 단계에서도 승차 구간 의미 손실 |
| `NoLate_FE/src/modules/schedule/routePlanner/routePlannerRouteInfo.ts:88` | BUS·SUBWAY·TRANSFER 외는 WALK 반환 | ETC가 도보 단계로 표시됨 |

배포 빌드의 대중교통 공급자는 ODsay다. `transitProviderConfig.ts:3`에서 TMAP은 명시적으로 선택한 개발·테스트 빌드에만 허용한다. 따라서 현재 증상의 1차 수정 대상은 ODsay를 사용하는 프런트 경로다. 정확한 출도착지·빌드·공급자 원본 응답을 이용한 기기 재현은 첫 구현 단계에서 추가한다.

## 공급자 계약과 데이터 한계

현재 FE와 BE는 모두 ODsay `/v1/api/maasRP`를 호출한다. 이 계약에서 `pathType=2`는 대중교통이며 현재 필터가 맞다. `pathSubType=4`는 시외교통이고, 구간 `trafficType`은 4가 열차, 5가 고속버스, 6이 시외버스다. **pathType 필터를 제거하거나 다른 API의 숫자 코드를 섞는 방식으로 고치지 않는다.** [ODsay 공식 API Reference](https://lab.odsay.com/guide/releaseReference)

maasRP의 SearchTime과 출도착 시각은 입력 출발시각과 구간 이동시간을 조합한 예상값이다. 실제 운행 시간표를 기반으로 경로를 찾는 기능은 아니라는 것이 공식 관리자 답변이다. 현재의 `providerTimeBasis: route_estimate` 구분을 유지한다. [ODsay 공식 설명](https://lab.odsay.com/community/boardView?seq=718)

실제 운행편을 보강할 후보는 TAGO [열차정보](https://www.data.go.kr/data/15098552/openapi.do), [고속버스정보](https://www.data.go.kr/data/15098522/openapi.do), [시외버스정보](https://www.data.go.kr/data/15098541/openapi.do)다. 시외버스는 현재 당일 배차만 제공한다는 제한이 있어 미래 일정 전체를 이 데이터 하나로 완성할 수 없다. 위 공개 API 응답에는 잔여석·예매 실행·승강장 정보가 없으므로 운행편 조회와 좌석 구매 가능 여부는 별도 상태로 관리한다.

## 검토 당시 저장과 ETA 제약

화면 오류를 고친 뒤 일정과 알림에서도 같은 구간이 유지되어야 한다.

지도 좌표가 없는 시외 응답이 실제로 발생하는지는 원본 응답으로 확인해야 한다. 현재 필터는 그런 응답 전체를 제거할 수 있다. 이미 선택한 이동시간 자체를 6시간으로 자르는 코드는 아니므로, 검색 시각 추정 상한과 저장 시간 검증을 혼동하지 않는다.

TMAP 개발·테스트 경로도 후속 정합성 대상이다. 서버 품질 검증은 TMAP 스키마와 BUS·SUBWAY에 고정되어 있고, `TmapTransitJourneyMapper`는 TRAIN·EXPRESSBUS 등이 포함된 여정을 제외한다. `TmapTransitJourneyMapperTest.kt:310`은 현재 이 제외 동작을 검증한다. 또한 `TransitRouteResponseQuality.kt:127`의 평균속도 상한 120km/h는 빠른 철도 경로를 거절할 수 있으므로 수단별 검증이 필요하다. 이 항목들은 배포 ODsay 화면 오류의 직접 원인과 구분한다.

## 목표 데이터 구조

일정 전체의 이동 수단은 기존 TRANSIT 계약을 유지하고, 내부 구간을 확장한다. 아래는 기존 ScheduleTravelPlan과 routeJson을 확장할 논리 구조 제안이며, 동일한 이동 계획 테이블을 새로 복제하자는 의미는 아니다.

```text
PersonalJourneyPlan
  schemaVersion, revision, scheduleId, memberId
  origin, destination, targetArrivalAt
  legs[]
    kind: WALK | BUS | SUBWAY | TRAIN | EXPRESS_BUS | INTERCITY_BUS | UNKNOWN
    from, to: 이름, 좌표, 공급자별 역 또는 터미널 ID
    duration, distance, geometry, geometrySource
    timingBasis: ROUTE_ESTIMATE | TIMETABLE | USER_CONFIRMED_TICKET
    departureAt, arrivalAt, serviceDate, serviceIdentity
    bookingState: UNBOOKED | USER_CONFIRMED | CANCELLED
    locked, ticketRef, source, fetchedAt
```

같은 버스·철도 노선이라도 다른 날짜·출발시각이면 다른 운행편이다. 버스에 고유 편 번호가 없으면 운행일·사업자·노선·출도착 터미널·출발시각의 조합을 사용하고, 충분한 식별 근거가 없으면 자동 일치를 확정하지 않는다. 승차권 인식은 사용자가 가져온 표의 확인 근거이며 발급사 서버의 예약 유효성 확인과는 구분한다.

승강장·탑승홈은 출처와 확인 시각을 가진 선택 필드다. 역 입구 좌표나 표의 역명만으로 정확한 홈까지 안내했다고 표시하지 않는다. 기존 서울 지하철의 급행 여부와 KTX 등 열차 종류도 별도 속성으로 유지한다.

## 단계별 구현과 완료 기준

### P0 시외버스 도보 오표시 복구

첫 구현 묶음은 실제 사용자 증상에 집중한다.

1. 시외 구간을 포함한 ODsay 응답을 민감정보 없이 fixture로 확보한다. 원본 trafficType과 각 변환 단계의 종류를 비교한다.
2. FE의 TransitLegKind, RouteMode, RouteStepType에 기차·고속·시외버스를 추가한다. 분산된 BUS·SUBWAY 조건을 공통 승차 판정으로 정리하되 실시간 도착 조회 지원 여부는 별도로 둔다.
3. ODsay parser, 경로 요약, 환승 횟수, 지도 선형과 마커, 진행 막대, 타임라인, 저장용 RouteInfo를 함께 수정한다.
4. 모르는 구간은 UNKNOWN 또는 기존 ETC 의미를 유지한다. 도보로 강제 변환하거나 중간 구간을 삭제하지 않는다.
5. 구버전 저장 경로에 원래 수단 근거가 없으면 추정으로 복구하지 않고 재검색 대상으로 둔다. 재검색이 끝나기 전 기존 알림 상태를 임의로 새 ETA로 승격하지 않는다.

주요 파일: `odsayApi.ts`, `tmapApiCore.ts`, `routeInfo.ts`, `routePlannerRouteInfo.ts`, `transitRouteSegmentPolicy.ts`, `routeTransitGeometryBuilder.ts`, `routeTransitLegCoordinates.ts`, `transitMarkerPresentation.ts`, `RouteStepTimeline.tsx`.

완료 기준: 시외버스 단독·시내버스와 시외버스 혼합·기차 포함 fixture가 검색 결과, 상세 지도, 일정 저장 후 재열기에서 같은 교통수단으로 표시된다. 실제 도보 구간만 도보가 된다. 기존 시내 경로가 유지되며, 미지원 장거리 ETA를 확정 출발 알림처럼 표시하지 않는다.

### P1 저장과 서버 재조회의 구간 정합성

P0의 새 유형이 서버에서 사라지지 않도록 FE·BE 계약을 맞춘다.

- TransitLegMode, isRide, SelectedTransitRouteDecoder, ODsay mapper, EffectiveTransitRoute 및 FE API 타입을 함께 확장한다.
- routeJson에 schemaVersion을 두고 기존 경로 읽기 호환성을 유지한다. 새 유형을 모르는 앱 버전에는 기능 노출을 제한하거나 명시적인 호환 처리를 제공한다.
- 유효한 구간·소요시간이 있으면 지도 선형이 없어도 경로 목록과 저장을 허용한다. 위치 근거가 있는 역·터미널 마커는 표시하되, 임의 직선을 실제 철도·버스 운행 경로로 표시하지 않는다. 검색과 저장 모두의 geometry 필수 조건을 점검한다.
- 새 승차 수단을 추가했다고 기존 서울·TAGO 시내버스 실시간 API를 무조건 호출하지 않는다. 수단별 시간표·실시간·예매·지도 지원을 나눈다.
- TMAP을 허용하는 개발 빌드도 같은 유형 보존 규칙을 적용하고, 품질 검증을 공급자 스키마와 수단에 맞춰 분리한다.
- 장거리 구간이 누락되거나 ETA 근거가 부족하면 저장 경로와 예상 시간은 보존하되, 불완전한 값으로 자동 알람을 갱신하지 않는다.

완료 기준: 동일 경로를 `검색 → 저장 → 앱 재시작 → 서버 재조회`해도 구간 순서·수단·시간 근거가 유지된다. 지도 선형이 없는 유효 경로, 구버전 경로, 공급자 오류, 알림 비활성 상태도 회귀 검증한다.

### P2 실제 운행편과 전체 이동 시간 연결

2026-10-12 신청 후 재검증: 사용자가 세 API 활용신청을 완료한 뒤 열차 `TrainInfo`, 고속버스 `ExpBusInfo`, 시외버스 `SuburbsBusInfo`의 도시 목록 모두 HTTP 200·결과 코드 `00`을 확인했다. 이전 HTTP 403은 해결됐다. 수서→공주 열차 14편, 서울경부→공주 고속버스 31편이 조회됐다. 서울남부→공주 및 부산서부→진주 시외버스는 정상 응답의 0건이며, 이를 실제 운행 중단이나 전국 노선 미운행으로 해석하지 않는다. TAGO가 제공하지 않는 노선·날짜는 공식 예매처 확인이 필요하다. 키·토큰·인증 쿼리는 증거에서 제외한다.

최초 구현은 P2의 **공공 시간표 조회 부분**이었다. 경로의 장거리 구간에서 시간표 화면을 열고, 공급자별 역·터미널 ID를 사용자가 확인해 선택한다. 같은 이름의 다른 ID를 자동 병합하지 않는다. 열차·고속버스는 날짜를 지정하고 시외버스는 당일만 조회한다. 미래 시외버스 날짜는 공급자 호출 없이 `DATE_UNSUPPORTED`를 반환한다. 조회 실패·접근 거부·한도 초과·운행편 없음은 별도 상태이며, 모든 운행편은 `TIMETABLE`·`UNCONFIRMED`다. 조회만으로는 기존 routeJson과 ETA를 덮어쓰지 않는다. 후속으로 구현한 명시적 편 선택·여정 재조합은 다음 절에 기록한다. 예약 확정은 아직 지원하지 않는다.

신규 인증 API는 `/api/intercity/cities`, `/stops`, `/services`이며 `kind=TRAIN|EXPRESS_BUS|INTERCITY_BUS`를 받는다. 역·터미널 조회와 운행편 조회는 페이지당 최대 100건이다. 도시·터미널 목록은 24시간, 운행편은 5분 캐시하며 최대 256개 항목과 동일 요청 병합을 적용한다. API별 키 `TAGO_TRAIN_API_KEY`, `TAGO_EXPRESS_BUS_API_KEY`, `TAGO_INTERCITY_BUS_API_KEY`는 공통 `TAGO_API_KEY`로 대체할 수 있다. 같은 공공데이터포털 키라도 각 API의 활용신청은 필요하다.

앞선 시간표 조회 단계 검증은 새 BE 소스를 loopback 5524·별도 메모리 H2에서 실행하고, 실제 TAGO/TMAP adapter 및 정상 가입·로그인 계정으로 수행했다. 기존 서버와 사용자의 시뮬레이터는 재시작하지 않았다.

- 실제 API 통합: 열차 14편·고속버스 31편·시외버스 정상 0건, 캐시 조회 시 fetchedAt 동일, 미래 시외 날짜 미지원, 잘못된 ID namespace HTTP 400, 미인증 HTTP 403 확인.
- 실제 iOS E2E: `testIntercityLiveTimetableSearchSaveReopen` 1개 통과·실패/스킵 0개. 경로 검색→기차/고속 시간표 조회→시외 미래 날짜 및 0건 표시→조회 닫기→원래 경로 저장→앱 종료/재실행→TRAIN 상세 복원까지 확인했다. 조회한 운행편을 경로에 적용하는 테스트는 아니다.
- BE 2 suites / 44 tests, FE 2 suites / 11 tests, typecheck 통과. 수정 파일 ESLint 오류 0개이며 기존 화면의 inline-style 경고 5개는 남아 있다. 55개는 이번 실행의 합계이며 이전 173개·39개와 중복해 누적 집계하지 않는다.

#### P2 후속: 선택 편과 앞뒤 이동 연결

공공 시간표에서 미래 운행편을 고르고, 현재 경로의 승하차 장소와 같은 지점인지 확인한 뒤 적용한다. TAGO 역·터미널에는 좌표가 없으므로 선택 ID를 이름만으로 좌표에 자동 연결하지 않는다. 현재 경로의 좌표를 명시적 확인 후 사용한다. 장거리 구간이 한 개인 경로를 지원하며 좌표 누락·복수 장거리 구간은 적용을 거절한다.

선택 편의 출발·도착시각을 고정하고, 동일한 경로 공급자 경계에서 접근 경로와 도착 후 경로를 다시 조회한다. 접근이 늦으면 최대 세 번 더 이른 출발로 재조회하며 다른 열차·버스로 자동 교체하지 않는다. 탑승 준비 5~120분(기본 15분), 하차 후 여유 0~120분(기본 5분)은 별도 준비·대기 구간이다. 이는 실제 탑승홈이나 역 내부 동선을 검증한 시간이 아니다. 재선택 시 이전 준비시간을 중복하지 않고, 취소·화면 종료·일정 변경 뒤 도착한 응답은 적용하지 않는다.

새 선택 경로는 schemaVersion 3에 선택 편·조회/선택 시각·사용자 확인·여유시간·연결 시각을 저장한다. 기존 경로는 schemaVersion 2 계약을 유지한다. 전체 경로는 `anchored_journey` / `route_estimate`, 선택 편만 `TIMETABLE` / `UNCONFIRMED`다. 총 운임은 확인되지 않아 기존 추정 총액을 재사용하지 않는다. 상세의 출발 안내도 연결 경로의 예상 값으로 표시한다.

일정 시각을 수정해도 선택 편 시각을 역산해 움직이지 않는다. 서버는 편 시각·전체 구간 연속성·준비 여유·일정 시작 전 도착을 구조적으로 검사해 모순된 저장을 거절한다. 이 검사는 실제 예매나 공급자 응답의 진위 확인을 대신하지 않는다. 기존 `TRANSIT_INTERCITY_TIMETABLE_UNAVAILABLE` ETA guard는 유지해 시내 교통의 검증 상태로 장거리 편과 알림을 자동 갱신하지 않는다. 기기 알림의 실제 전달 검증은 P5에 남아 있다.

- FE 8 suites / 116 tests 통과. 자정 통과·초 단위 시각·늦은 접근·잘못된 연결·재선택·취소·일정 시각 수정·지도 정규화·저장 복원 회귀를 포함한다. typecheck 통과, ESLint 오류 0개·기존 inline-style 경고 5개.
- BE 3 suites / 51 tests 통과(시간표 14, 선택 여정 검증 7, ETA 30). 새 BE 소스를 별도 loopback API·메모리 H2에서 실행했다.
- 실제 API E2E 2개 통과. 2026-10-13 수서→공주 12:20→13:12 열차와 서울경부→공주 11:05→12:35 고속버스의 TAGO 편을 적용했다. 연결 경로는 실제 TMAP 재조회 후 생성→DB 재조회→정상 수정→출발 시각 불일치 수정 거절→원본 보존을 확인했다. 전체 구간의 최초 검색 자료는 이전에 캡처한 실제 TMAP 응답이다.
- 실제 iOS 화면 E2E `testIntercitySelectedServiceSaveReopen` 최종 실행 1개 통과·실패/스킵 0개. 실제 경로 검색→수서·공주 역 선택→2026-10-13 12:20 편 선택→동일 승하차 장소 확인→앞뒤 경로 연결→알림 비활성 일정 저장→저장 날짜 선택→앱 종료/재실행→12:20·13:12 및 `예매 미확인` 복원을 확인했다. 초기 실패와 시뮬레이터 연결 중단은 별도 기록했다. 전용 Metro의 자동 새로고침을 끄고(`CI=1`), 비활성 공유 기능의 재실행 안내창은 실제 확인 버튼으로 닫았다.

[선택 여정 검증 기록](../../../NoLate_FE/e2e/evidence/intercity-2026-10-12/intercity-selection-validation.json), [동일 장소 확인](../../../NoLate_FE/e2e/evidence/intercity-2026-10-12/selected-service-mapping.png), [재실행 후 선택 편](../../../NoLate_FE/e2e/evidence/intercity-2026-10-12/selected-service-reopened-timeline.png)에 공개 증거를 저장했다. 최종 XCTest 원본은 로컬 `/private/tmp/nolate-intercity-selection-ui-20261012-14/result.xcresult`다. 이전 단계의 임시 경로는 당시 실행 위치이며, 보존된 JSON·PNG와 구분한다. Android, 실제 편이 제공되는 시외버스 노선, 좌석·예매·탑승홈·알림 전달은 이번 검증에 포함하지 않는다.

공급자별 지원 범위와 남은 확장은 다음 기준으로 진행한다.

- 열차·고속·시외버스 시간표 adapter와 역·터미널 ID 매핑을 만든다. 동명이역·도시별 터미널·공급자 ID 충돌을 처리한다.
- 요청 날짜 지원, 조회 실패, 운행 없음, 시간표 미제공을 구분한다. 미래 시외버스 정보가 없으면 예매 서비스 확인 또는 사용자의 편 입력을 제공한다.
- 최종 도착 마감과 선택한 운행편을 함께 고려한다. 접근 경로는 해당 편의 승차 마감에 맞추고, 도착 후 경로는 해당 편 도착 이후에 조회한다.
- 역·터미널 내부 이동 및 탑승 여유 시간은 별도 값으로 둔다. 제공되지 않은 내부 경로를 외부 도보 시간에 숨기지 않는다.
- 자정 통과, 환승 대기, 막차, 배차 간격, 일정 날짜 변경을 처리한다. 전체 구간 조합의 조회 횟수와 후보 수를 제한하고 캐시·중복 요청 병합을 적용한다.
- 6시간을 넘는 여정도 초기 검색 출발시각과 선택 후 실제 이동시간이 충돌하지 않도록 FE 검색 추정 정책과 BE 허용 시간 범위를 맞춘다.
- 편의 예약이 확정되면 그 구간을 잠근다. 접근 교통이 늦어져도 예약편을 다음 편으로 자동 변경하지 않고 연결 불가 상태를 표시한다.

```text
집 권장 출발시각
  = 확인된 승차 마감시각
    − 집에서 역 또는 터미널까지의 접근시간
    − 필요한 내부 이동시간
    − 사용자 또는 서비스가 설정한 탑승 여유시간

최종 예상 도착시각
  = 선택한 편의 도착시각
    + 필요한 하차와 환승시간
    + 최종 목적지까지의 이동시간
```

탑승 여유와 내부 이동이 이미 포함된 값이면 다시 더하지 않는다. 출발시각과 승차 마감시각을 혼동하지 않는다.

완료 기준: 예매한 10시 편은 교통량 변화나 ETA 재조회 후에도 10시 편으로 유지된다. 시간표가 없는 상태와 확인된 운행편이 화면·알림에서 구분되고, 목표 도착 마감에 맞지 않는 조합은 추천 가능한 경로로 확정되지 않는다.

### P3 공식 예매 서비스 연결

경로별로 공식 예매 사이트를 열 수 있게 한다. [코레일](https://www.korail.com/), [버스타고](https://www.bustago.or.kr/), [티머니 시외버스](https://txbus.t-money.co.kr/) 등이 대상이며 실제 노선의 취급 서비스와 공식 주소를 배포 전에 확인한다.

일반 웹 연결을 먼저 제공하고, 공식 지원과 실제 기기 동작이 검증된 서비스부터 앱 이동·출도착지·날짜 자동 입력을 추가한다. 공개된 범용 딥링크 사양이 확인되지 않은 기능은 지원한다고 약속하지 않는다. 예매 링크를 눌렀다는 사실만으로 구매 완료 상태를 만들지 않는다.

완료 기준: 앱 설치·미설치 모두에서 사용자가 예매 화면에 도달하고 NoLate로 돌아올 수 있다. 예매 전 이동 계획은 유지되며 표를 가져오기 전에는 예약이 확정되지 않는다. 기본 웹 링크는 P1과 병행할 수 있다.

#### P3 1차: iOS 기차 공식 웹 연결 — 최초 구현 기록

선택한 기차 경로 카드, 기차 시간표, 가져온 표 요약, 저장된 일반 기차 경로의 타임라인에
`코레일 공식 예매 열기`를 제공한다. iOS의 HTTPS 열기로 기본 브라우저에 이동하며,
공식 앱의 범용 링크 처리 여부는 OS가 결정한다. 검증되지 않은 커스텀 스킴이나 자동
출도착지·날짜 입력은 추가하지 않았다. Android에는 이 버튼을 노출하지 않는다.
가져온 표가 있는 경로 상세는 시트를 펼친 뒤 예매 버튼을 표시한다. 접힌 시트에서는 기존
요약과 펼치기 버튼을 유지해 추가 버튼이 경로 상세 진입을 가리지 않게 했다.

URL은 `https://www.korail.com/`으로 고정한다. 일정·좌표·표·로그인 정보를 쿼리로 보내지
않으며 버튼을 눌러도 선택 편, 승하차 확인, 경로, 저장 상태, 예매 검증 상태를 변경하지
않는다. 중복 누르기는 한 번만 처리하며 URL 열기 실패 시 다시 시도할 수 있다.
웹 예매의 네트워크 오류와 로그인·결제는 예매처에서 처리한다.

번들 공급자 사전 검사로 TMAP 적용을 확인한다. 제품 Metro 설정과 `.env`는 변경하지 않는다.

#### P3 2차: iOS 코레일 앱 우선 연결

### P4 승차권 가져오기와 예약편 고정

목표 범위는 이미지·PDF 공유 수신, 인식 확인, 기존 여정 연결과 변경·취소 처리다. 아래 1차·후속 기록은 2026-10-12 시점이다. 버스·PDF·중복 방지의 최신 구현 상태는 위 2026-10-13 절을 따른다. 앱 내 가져오기함·Android 수신·원본 보관은 아직 제공하지 않는다.

- 첫 버전은 사진·스크린샷 가져오기와 수동 수정을 우선한다. PDF는 파일 수신·텍스트 추출·스캔 문서 OCR을 추가한 뒤 제공한다.
- 날짜, 출발지, 도착지, 출발·도착 시각, 열차번호 또는 버스 등급, 좌석, 표 상태를 추출한다. 기존 일반 일정 OCR의 300자 축약 규칙을 티켓에 그대로 적용하지 않는다.
- 인식 결과를 사용자에게 확인받고 기존 이동 계획의 장거리 구간과 연결한다. 여러 표·왕복 표·복수 승객·중복 공유를 구분한다.
- 예약 확인서, 승차권, 취소·환불 내역을 구분한다. 사용자가 확인한 표는 잠긴 구간으로 만들고 변경·취소 시 계획과 알림도 갱신한다.
- 원본 파일과 티켓 정보는 개인 이동 계획에 소유권을 둔다. 공유 일정 참가자에게 예약번호·바코드·개인정보가 자동 노출되지 않게 한다. 원본은 오프라인 보관과 삭제를 지원한다.
- 티켓 원본 보기와 공식 앱 열기를 제공한다. 바코드 표시가 실제 승차권으로 허용되는지는 발급사별로 확인한다.

완료 기준: `예매 서비스 이동 → 표 가져오기 → 인식 확인 → 기존 구간 연결 → 예약편 고정 → 출발 알림 재계산`이 이어지고, 앱 재시작·오프라인·중복 공유 후에도 표와 계획이 유지된다.

#### P4 1차: iOS 기차 정보 가져오기

Apple Wallet 없이 iOS 공유 확장에서 이미지 한 장 또는 상세 텍스트 한 개를 받는다.
이미지는 기기 내 Vision OCR로 읽고 날짜·출발/도착역·시각·열차번호를 편집 가능한 화면에
표시한다. 불확실한 항목은 비워 두며 오늘 날짜나 자정 이후 도착을 임의 추정하지 않는다.
원본과 일치한다는 명시적 확인 전에는 저장할 수 없고, 수정하면 확인 상태를 해제한다.
미래 출발·24시간 이내 도착·한국 시간의 유효한 날짜를 검사한다.

확인된 구조화 정보만 개인 카테고리에 도착 시각의 일정으로 저장한다. 원본 이미지·OCR 원문·
QR·예약번호·좌석·결제정보는 업로드하거나 보관하지 않는다. 출도착역 이름만 저장하며
좌표를 임의 생성하지 않는다. 아직 경로를 연결하지 않은 일정은 `NOT_CONFIGURED`로
표시하고, 일반 일정 상세와 경로 상세 양쪽에 가져온 승차권 요약을 보여 준다.

경로 설정에서 실제 승하차 장소를 확인한 뒤 가져온 열차를 선택하면 TAGO 재조회 없이
`TICKET / UNVERIFIED` 시각을 고정하고 실제 TMAP 접근·도착 후 경로를 연결한다.
최종 목적지까지 가려면 일정 도착 시각도 그 이동에 맞게 설정해야 한다. 다른 편이나
일정 역산 시각으로 표 시각을 바꿀 수 없으며, 접근이 늦거나 최종 도착 제한을 넘으면
적용을 거절한다. 서버는 원본 승차권 정보와 연결 편·구간 연속성의 일치를 검사한다.
이는 실제 구매·취소 여부의 검증이 아니므로 `예매 상태 미검증`을 계속 표시한다.
원래 표와 탑승홈은 예매처에서 확인하며, NoLate 화면은 탑승용 승차권이 아니다.

실제 로컬 API E2E 1개가 통과했다. API 테스트는 합성 승차권으로 저장→TMAP 앞뒤 경로
실호출 2회→DB 복원→정상 수정→시각·열차번호 불일치 거절을 확인했다.

공유한다는 가정도 하지 않는다. 외부 공유를 제공하지 않는 화면에서는 사용 가능한
승차권 이미지·상세 텍스트 공유 경로를 별도로 확인해야 한다.

2026-10-12 1차 검증 당시 남은 항목: 버스·PDF·여러 표/왕복/다중 승객·중복 공유·원본 보기·오프라인 원본·취소/재발권 동기화·
공식 예매 앱의 실기기 검증·알림 재계산과 전달은 남아 있다. 따라서 전체 P4 완료로 표시하지 않는다.

#### P4 후속: 합성 이미지로 전체 iOS 경로 연결 검증

합성 기차 이미지의 실제 공유 시트 수신부터 OCR 확인·저장·재실행, 최종 도착 희망 시각 수정,
출발지와 최종 목적지 설정, 가져온 열차 연결, 일정 저장, 두 번째 재실행까지 iOS 화면 E2E가
통과했다. 수서 12:20 → 공주 13:12를 고정하고 서울남부터미널에서 접근해 공주터미널까지
이어지는 앞뒤 경로는 실제 TMAP으로 조회했다. 최종 도착 희망 시각은 20:00이며 열차 시각과
구분해 저장된다. 승하차 장소는 사용자가 같은 장소임을 명시적으로 확인한다.

경로 연결 전 일정 수정에서 가져온 표와 이름만 있는 출발지가 사라지던 문제를 두 저장
경로에서 수정했다. 가져온 표의 역 이름을 임의로 좌표화하지 않으며, 경로 미설정 상태의
설정 버튼은 일정 수정으로 연결해 최종 목적지와 희망 시각을 함께 저장한다. 타임라인의
탑승 문구 정리 과정에서 `승차권`이 `권`으로 잘리던 표시도 수정했다.

이번 후속 검증은 FE 12 suites / 160 tests, typecheck, 변경 파일 ESLint 오류·경고 0개,
API E2E 1개와 iOS 화면 E2E 1개가 통과했다. API 연결 호출은 TMAP 2회, TAGO 0회이며,
다른 TAGO 사례 2개는 이름 필터로 미선택했다. iOS 최종 실행은 210.558초, 실패·스킵 0개다.
서버 조회에서도 실제 화면에서 생성한 일정의 `READY`, 최종 목적지, 고정 열차 시각,
8개 이동 구간과 알림 비활성화를 확인했다. 이전 검증 수와 합산하지 않으며 BE·Swift 파서
소스는 이번 후속 작업에서 변경하지 않았다.

따라서 P4 전체 완료를 의미하지 않는다.

### P5 이동 중 안내와 안정화

저장한 전체 여정을 기존 [이동 중 길안내 로드맵](../../../JOURNEY_GUIDANCE_ROADMAP.md)의 상태기계와 연결한다. 진행 상태, 하차·환승 알림, Live Activity, 음성 안내는 같은 구간 ID와 revision을 사용한다. GPS만으로 정확한 승강장이나 열차 탑승을 확정하지 않고 수동 보정을 제공한다.

완료 기준: 시내 접근 → 예약편 탑승 → 하차 → 최종 이동까지 상태가 이어진다. 예약편을 놓친 경우와 시간표가 바뀐 경우에 중복·잘못된 알림을 막고, Android에서도 핵심 여정 기능을 동일하게 검증한다.

## 출시 단위와 의존 관계

| 출시 단위 | 포함 단계 | 사용자에게 제공할 결과 | 통과 조건 |
| --- | --- | --- | --- |
| 시외 길찾기 복구 | P0와 P1 | 시외버스·기차가 올바른 수단으로 보이고 저장됨 | 사용자 증상 재현 테스트 및 저장·재조회 정합성 |
| 운행편에 맞춘 이동 계획 | P2와 P3 | 실제 편을 선택하고 예매 서비스로 이동 | 날짜별 시간표 지원 범위와 연결 가능성 검증 |
| 승차권 기반 개인 여정 | P4 | 가져온 표로 예약 구간 고정, 원본 보기, 출발 알림 | OCR 확인·원본 보관·변경과 취소 처리 |
| 이동 중 안내 | P5 | 탑승·하차·환승 안내 | 여정 상태와 알림의 기기 검증 |

전체 아키텍처 교체나 모든 시간표 API 연결을 P0의 선행 작업으로 두지 않는다. P0와 P1을 먼저 작은 출시 단위로 완성한다. 이후 기간은 실제 시외 응답, 미래 날짜 데이터 지원, 예매 서비스 연결 범위가 검증된 뒤 산정한다.

새 구간을 읽을 수 있는 서버 계약을 준비한 뒤 앱 기능을 단계적으로 노출한다. 수단별 후보 수, UNKNOWN 변환, 선형 누락, 저장 복원 실패, 시간표 지원 범위, ETA 갱신 실패를 구분해 관측하고 시외 기능을 독립적으로 중단할 수 있게 한다. 티켓 원문과 예약번호는 운영 로그에 남기지 않는다.

최초 소스 검토 시점의 기존 오프라인 단위 테스트는 FE 5개 suite 87개, BE 4개 대상 클래스 48개가 통과했다. FE 대상은 odsayApiParsing, transitProviderSelection, routingService, routeInfo, scheduleRouteTiming이다. BE 대상은 TransitRouteServiceTest, TmapTransitJourneyMapperTest, OdsayTransitJourneyMapperTest, SelectedTransitRouteDecoderTest다. 이 결과는 수정 전 기준선이며 현재 실행 결과는 문서 상단에 별도로 기록했다.

2026-10-13에 버스 앱 우선 연결·공식 웹 대체 연결·버스/PDF 가져오기·중복 방지를 구현했다. 현재 결과는 문서 상단의 최신 절을 따른다. 동서울→속초의 실제 경로 검색·저장·복원, 인천공항2터미널→청주의 실제 당일 편 선택·자정 통과 연결·저장·재실행 복원은 확인했다. 복수 장거리 편 연결, 원본·오프라인 보관, 변경/취소 자동 동기화, P5 알림·여정 안내 전체는 남아 있다. 실제 코레일 앱 이동·공유 형식은 실기기 후속 대상이며 사용자 요청 전까지 보류한다. 미구현·미검증 단계를 E2E 통과로 표시하지 않는다.
